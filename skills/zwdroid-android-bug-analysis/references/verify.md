# verify.md — S5 源码验证(条件状态)

## 准入:源码开关
S5 **默认不进入**。仅当**同时**满足才置源码开关为开:
(a) 运行时 CLAUDE.md 配了 `{{AOSP_ROOT}}` 且路径存在;(b) 用户本次明确要求"结合源码验证/给修复建议"。
二者缺一 → S4 直接产出**形态 B**结论(日志级/接口边界)进 S6a。
默认路径的交付是"责任组件 + 触发条件 + 证据链",**不承诺源码级归因——这是设计定位,非能力缺陷。**

## 进入 S5 后的流程
1. **先书面列出**:若假设为真,源码中应存在什么(类/方法/调用关系/日志打印点)。
2. **grep 实证每一项**:`aaos-grep.py <pattern> [--scope framework|vendor|all] [--type java|cpp|aidl]`。
   **任何类名/方法名/路径在写入结论前必须有 grep 命中记录(R2)**。grep 未命中本身是信号——
   预期签名不存在,不得断言该类/方法存在。
3. **版本一致性**:确认命中文件属于 `{{AOSP_BRANCH}}`(本项目 android-12.0.0_r34)当前分支,
   警惕多分支 checkout 串扰。
4. **日志↔代码互锁**:找到日志行对应的打印语句,确认参数语义与日志实际值一致
   (完成 R3 三对齐的代码侧闭环)。
5. **结果三态**:
   - **证实** → 证据链闭合,S6a **形态 A**(落到源码 path:line + 修复方向)。
   - **证伪** → 回 S4,原假设移入"已排除"。
   - **无法判定** → 该候选在 ledger 标"无法判定"并**冻结**(不再选取),记录"需要什么才能判定",回 S4 取下一候选。

## 闭源边界(形态 B,即使源码开关开也可能止步于此)
假设指向闭源组件(vendor HAL 二进制/MCU/硬件)时,验证对象改为**接口契约**:
grep 实证接口定义(AIDL/HIDL)与调用侧实现,结合日志证明组件**违约行为**(超时未回/非法返回值)。
证据链止于组件接口边界即视为闭合 → S6a 形态 B,结论指向"接口 + 违约行为",不强求闭源内部 file:line。
**禁止**因拿不到闭源 file:line 而误走 S6b 或硬凑源码归因(R7)。
